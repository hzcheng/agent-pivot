# 会话内 Markdown 文档工作区 PRD

日期：2026-09-09

状态：草案，待评审

## 1. 背景

Agent Pivot 的 AI Conversation 是用户阅读智能体输出、追问和派发下一步工作的地方。对方案、设计、复盘、迁移说明等长 Markdown 而言，当前对话式体验有两个问题：

- 用户需要先让 AI 将整份内容输出到对话里，才能逐段讨论；长文会淹没会话历史，且重复消耗上下文。
- 用户在普通编辑器中阅读文件时，难以把一个具体段落和一条 AI 讨论、修改建议或待办稳定地关联起来。

一个直觉方案是在 conversation 消息内直接展开 Markdown。但 conversation 是按时间滚动的历史，文档是需要反复定位、阅读和批注的工作对象。用户与 AI 多轮交互后，原始文档卡片会被滚走，文档与讨论也会失去可见的对应关系。

本功能因此不把 Markdown 做成一条无限变长的聊天消息，而是从 conversation 发起一个**会话内文档工作区（Document Workspace）**：文档有自己的稳定阅读面、滚动位置和批注锚点；围绕它的 AI 讨论仍属于同一个 conversation。

## 2. 目标

1. 用户可从 AI conversation 在相邻的专用 Markdown 工作区 Tab 打开一个文件，并在其中阅读和审阅它。
2. 用户可以选中某段文档添加批注，并把该批注连同精确文档上下文发送给当前 AI session。
3. 文档滚动与 AI 讨论滚动相互独立；无论讨论进行了多少轮，用户都不会丢失正在审阅的文档和位置。
4. AI 可以针对批注提出局部修改；用户能先查看 diff，再明确决定是否应用到文件。
5. 用户可随时打开同一文件的原生 VS Code editor，作为连续写作、多文件对照和高级编辑的出口。

## 3. 非目标

- v1 不实现多人实时协作、评论提及、通知或云同步。
- v1 不新建一个独立的 Dashboard tab，也不替代 VS Code 原生 Markdown editor / preview。
- v1 不支持任意二进制、富文本、Office 文档或 MDX；只支持工作区内的 UTF-8 `.md` 文件。
- v1 不让 AI 静默写入文件；任何文件变更都必须经过用户的明确应用动作。
- v1 不解决 Git merge conflict；文件在外部被修改时采用保守刷新和重新生成建议的策略。
- 不改变现有 conversation 评论及项目级批注的既有语义；本功能新增的是“文件锚定的文档评论”。

## 4. 产品定位与关键决策

### 4.1 入口在 conversation，工作面不属于聊天时间线

对话中的 Markdown 引用显示为紧凑文档卡片，而非全文：

```text
📄 architecture-plan.md
1,248 lines · Modified · 3 open comments
[在会话中打开] [在编辑器中打开] [更多]
```

点击“打开 Markdown 工作区”后，VS Code 在相邻编辑器组打开专用 Markdown 工作区 Tab。它仍绑定同一个 session / conversation，但与原 conversation 是两个独立 Webview；关闭工作区只关闭该 Tab，原 conversation 的阅读位置不变。

选择该方案的原因：

- 原 conversation 不会因文档阅读、评论或 AI 刷新而重绘、遮挡或丢失滚动位置。
- 避免一篇长文把时间线撑开，更避免用户在 AI 回复后找不到最初的文件链接。
- 为锚点、局部 diff、未处理批注数和恢复阅读现场提供稳定的 UI 容器。

### 4.2 原生编辑器是出口，不是主流程

工作区针对“阅读、审阅、讨论、局部改写”。用户需要连续编辑、查找替换、文件树或多文件并排时，点“在编辑器中打开”进入 VS Code 原生编辑器。两个入口始终指向同一个工作区文件。

### 4.3 M1 的文件范围与评论归属

M1 只允许打开**工作区中已存在的 `.md` 文件**。入口可以是 AI 输出中可解析到该文件的链接，或已有文档卡片；不支持从操作系统任意路径挑选文件，也不支持把 AI 临时生成但尚未落盘的 Markdown 作为文档打开。

文件评论以工作区文件为长期归属，conversation 仅记录“这条评论曾在哪个 AI session 中讨论”。因此关闭、归档或删除 conversation 不会删除文件评论。这个决定使评论能在不同 AI session 和多次审阅间延续，也避免把文件资产误当成聊天记录附件。

## 5. 信息架构与页面状态

### 5.1 普通 Conversation 状态

未打开文档时，conversation 保持现有时间线行为。文档卡片只展示标题、路径（必要时）、版本/保存状态和未处理批注数。

若某份文件仍是当前会话的活跃文档，在输入框上方固定显示上下文胶囊：

```text
📄 architecture-plan.md · Rollback strategy · 3 条未处理批注
[返回文档] [解除关联]
```

它解决了用户离开工作区并聊了多轮后，忘记当前讨论对象的问题。解除关联只移除当前会话的“活跃文档”提示，不删除文件和批注。

### 5.2 文档工作区状态

推荐宽屏布局如下：

```text
┌────────────────────────────────────────────────────────────────┐
│ ← 返回 Conversation   architecture-plan.md · 已保存       ×     │
│                         [在编辑器中打开] [更多]                 │
├─────────────────────────────────┬──────────────────────────────┤
│ Markdown 文档                    │ 与此文档的 AI 讨论           │
│  （独立纵向滚动）                 │ （独立纵向滚动）              │
│                                 │                              │
│ ## Rollback strategy             │ 用户评论 #4                  │
│  … [评论标记 4]                  │ “补充迁移失败时的恢复方案”   │
│                                 │                              │
│                                 │ AI 建议变更                   │
│                                 │ [查看 diff] [应用] [拒绝]    │
├─────────────────────────────────┴──────────────────────────────┤
│ Ask AI about this document…                                      │
└────────────────────────────────────────────────────────────────┘
```

- 默认是**双栏**：左侧是最大可读宽度的 Markdown 渲染面，右侧只展示与该文件相关的讨论、评论和修改建议。评论在正文边缘显示为紧凑的编号标记；点击标记后才在左侧边缘打开评论抽屉。抽屉关闭后不占用正文宽度，不设置常驻第三栏。
- 两侧滚动、焦点和恢复位置完全独立。右侧出现新 AI 回复不能令左侧滚动，也不能改变文档选区。
- 用户正在阅读文档时，新 AI 回复只在右侧标题显示“1 条新回复”提示，绝不自动滚动任一面板或抢夺焦点。
- 窄宽度下改为单列：文档和“讨论”在顶部可切换，当前模式固定；不得让两个可滚动区域强行挤到不可用宽度。
- 顶栏固定，不随任一内容区滚动；它始终提供返回、文件名、保存状态和原生编辑器出口。

### 5.3 回到 conversation

关闭 Markdown 工作区 Tab 后回到仍保留在原位置的 conversation。系统在原对话中保留或更新紧凑文档卡片；不会将文档全文、所有评论和 AI 回复重复复制回时间线。

## 6. 核心交互

### 6.1 打开、恢复和切换文档

- 用户可从 AI 输出中的工作区 `.md` 文件链接、现有文档卡片或当前活跃文档胶囊进入工作区；不支持未知路径、工作区外路径或尚未写入工作区的临时文本。
- 同一 conversation 的 Markdown 工作区 Tab 复用当前文档会话；打开另一份文件前保留前一份的阅读位置、折叠章节和侧栏筛选状态。
- 再次打开某文件时，恢复该 viewer 中最后的文档滚动位置；若文件版本变化，则跳至最近可解析的章节，无法恢复时回到顶部并提示。
- 文件不存在、移出工作区或无法读取时，工作区显示明确错误和“在编辑器中重新定位 / 关闭”操作，已存在的讨论记录不删除。

### 6.2 选择文本与添加评论

在可选择的 Markdown 正文中选中文本时出现浮动工具条：

```text
[添加评论] [问 AI] [解释]
```

- **添加评论**：在选区旁建立草稿评论。用户可以只保存，或填写后发送给 AI。
- **问 AI**：立即创建一条携带选区的文档问题，AI 在右侧讨论流回答，不产生文件改动。
- **解释**：适合概念说明、风险分析或术语解释，默认不建议改文件。

选区过长时，UI 显示完整长度并按限制截取随 prompt 发送的正文；始终保留章节路径与周边上下文，避免 AI 只看到一段无语义的孤立文本。

### 6.3 评论的双重可见性

一条文档评论同时是：

1. 左侧文档上的可定位批注（行内标记 + 按需打开的评论抽屉）；以及
2. 右侧讨论流中的结构化消息。

讨论消息至少显示文件名、章节路径、引用摘要和“定位到原文”。点击定位会将左侧文档滚动到评论锚点并短暂高亮，但不会改动右侧讨论的滚动位置。

评论可处于 `draft`、`sent`、`resolved`、`outdated` 状态：

- `draft`：只在本地保存，尚未交给 AI。
- `sent`：已作为上下文发送给 AI，可继续追加讨论。
- `resolved`：用户手动标记完成，默认不再占用评论轨道主列表。
- `outdated`：文件变更后无法可靠重定位；保留其引用快照和讨论，可由用户重新锚定或关闭。

### 6.4 将评论发送给 AI

发送时插件不依赖“当前屏幕上能看见文档卡片”，而使用文档对象和评论锚点构造结构化上下文。概念 prompt：

```text
正在审阅文件：docs/architecture-plan.md
章节：Rollback strategy
用户评论：需要补充数据库迁移失败时的恢复方案。
引用文本：
> The migration runs before the service is restarted.
```

发送还应包含适量前后文、当前文件版本标识和明确任务类型（提问 / 改写 / 解释）。发送成功后：

- 评论状态从 `draft` 变为 `sent`；
- 右侧讨论流追加用户消息；
- 当前 AI session 接收 prompt，复用既有的 session staging / submit 管线；
- 左侧选区与文档位置保持不变。

发送失败则保留草稿和锚点，显示可重试错误，不创建“已发送”的假记录。

### 6.5 AI 修改建议与应用（M3）

当请求类型是“改写”，或 AI 自己提出可执行的文件改动时，UI 使用建议变更卡片，而非直接把完整 Markdown 重发到聊天：

```text
建议修改 · Rollback strategy
3 additions, 1 deletion
[查看 diff] [应用] [拒绝] [继续讨论]
```

- “查看 diff”在左侧对应段落内联展示，或在紧凑 diff 面板中展示；不可直接覆盖正文。
- “应用”前检查文件版本和目标锚点仍匹配。成功后写入最小范围 patch，并在阅读器中保留“撤销上一次 AI 变更”；撤销同样重新检查当前文件版本和唯一锚点，绝不覆盖其后的用户修改。应用 patch 不会自动 resolve 原评论，评论是否解决始终由用户决定。
- Windows 首发版本保持建议卡、diff 和“在编辑器中打开”，但禁用直接应用/撤销；这是为避免受目录 junction 置换影响的非原子写入。用户可在原生 editor 中完成变更。
- 若文件已被外部修改、目标范围不再匹配或 patch 无法干净应用，则禁止应用，标记建议为 `outdated`，并提供“基于当前文件重新生成”的操作。
- “拒绝”只关闭本建议，不删除原评论与讨论历史。

## 7. 评论锚定与数据原则

行号不是稳定锚点。每个文件评论应保存足以在内容变动后重新定位的信息：

```ts
interface MarkdownDocumentComment {
    id: string;
    documentUri: string;
    documentVersion: string; // 内容 hash 或等价版本标识
    anchor: {
        selectedText: string;
        prefix: string;
        suffix: string;
        headingPath: string[];
        rangeHint?: { startLine: number; endLine: number };
    };
    text: string;
    status: 'draft' | 'sent' | 'resolved' | 'outdated';
    createdAt: number;
    updatedAt?: number;
    conversationRef?: { provider: string; sessionId: string; messageId?: string };
}
```

重定位策略按可靠性排序：精确选区 + 前后缀 → 章节路径内匹配 → 行号提示。若存在多个匹配或没有可靠匹配，绝不猜测性地把评论移到另一段文本上，而是标记 `outdated` 并要求用户确认。

评论以规范化的工作区相对文件标识为持久化 key；`documentUri` 用于当前窗口定位，conversationRef 仅保存最近或关联的讨论来源。删除或归档 conversation 不得删除用户写在文件上的评论。多根工作区的根标识、文件重命名和移动时的迁移规则由技术设计补充，但不得退化为按 conversation 存储。

## 8. 与现有产品能力的关系

| 能力 | 与本文功能的关系 |
| --- | --- |
| AI Conversation viewer | 提供入口、同一 AI session、右侧文档讨论流和提交管线。 |
| 现有 session 评论 | 继续锚定 conversation 输出；不应被文件评论替代或混淆。 |
| 项目级批注 | 仍用于跨 session 的项目想法/待办；文件评论解决“这份文档的这一段”。后续可提供“转为项目笔记”。 |
| VS Code editor | 文件深度编辑和多文件操作的出口；不是本功能的重复实现。 |
| Markdown preview | 可复用渲染能力，但需要补足文档锚点、评论轨道、diff 和状态恢复。 |

## 9. 成功指标

上线后应关注：

- 从打开文档到首次发送文件锚定问题的完成率与中位耗时，并与复制粘贴 Markdown 到对话的基线对比。
- 发送给 AI 的文档评论中，带稳定锚点的比例（目标 100%）。
- AI 修改建议的查看 diff、应用、拒绝和过期比例。
- 发送文件评论后用户是否继续完成审阅（继续评论、应用建议或手动 resolve），而非仅记录点击次数。
- 用户从工作区打开原生 editor 的比例；它用于识别会话内审阅与深度编辑的边界，不单独作为成功或失败信号。
- “返回 Conversation”后重新打开相同文档并成功恢复位置的比例。

不以 AI 生成的全文 Markdown token 数为成功指标；该功能的价值恰恰是避免无必要的全文重复输出。

## 10. 分期建议

### M1：稳定阅读面与文件上下文

- 仅支持从 conversation 打开工作区内已存在的 `.md` 文件。
- conversation 文档卡片、相邻 Markdown 工作区 Tab、独立滚动和固定顶栏。
- 打开原生 editor、阅读位置恢复、活跃文档胶囊。
- 只读 Markdown 渲染，不支持评论和写回。

### M2：文件锚定评论与 AI 讨论

- 选区创建草稿评论、行内评论标记、按需评论抽屉和右侧结构化讨论。
- “问 AI / 解释”发送管线。
- 锚点持久化、基础重定位和 `outdated` 降级。

### M3：可控的局部变更

- AI 建议变更卡片、局部 diff、显式应用/拒绝。
- 文件版本检查、失败时重新生成。
- 评论 resolved 工作流及回归测试。

### 后续候选

- 评论转项目笔记、发送给另一个 AI session。
- 多文件审阅队列和跨文件引用。
- 导出审阅记录、评论筛选、搜索和批量 resolve。

## 11. 验收标准

1. 用户打开 Markdown 后，在右侧进行任意数量的 AI 交互，左侧文档的滚动位置、选区和顶栏均不被改变。
2. 用户关闭工作区后继续 conversation，可从文档卡片重新打开同一文件并恢复先前阅读位置。
3. 任何发送给 AI 的文件评论均携带文件标识、章节/锚点、评论正文和足以理解的引用上下文；不要求 AI 依赖聊天记录中的全文。
4. 从右侧任一文件评论或建议变更点击“定位到原文”，能正确定位并高亮；无法可靠定位时清楚显示过期状态，不能错误跳转。
5. AI 的任何文件修改建议在用户点击“应用”前都不会改变磁盘文件；文件版本冲突时不会覆盖外部变更。
6. 打开、刷新或关闭工作区 Tab 不会复制全文 Markdown、遮挡或破坏既有 conversation 滚动位置。
7. 键盘可操作所有核心控件，评论锚点、diff 和状态均具有可读的无障碍名称。
8. 用户阅读文档时，AI 新回复不会自动滚动、切换焦点或覆盖当前选区；用户可自行查看新回复。
9. 应用成功的建议变更可通过阅读器内“撤销上一次 AI 变更”安全撤销；撤销会在文件已变更或目标不唯一时失败关闭，且应用变更不自动将评论标为 resolved。

## 12. 待确认问题

1. AI 返回结构化 patch 的协议由哪一层定义、怎样兼容 Codex / Kimi / Claude？建议先使用统一的 host-side suggestion envelope，并允许无法结构化的回复退化为普通讨论，不自动生成 diff。
2. 多根工作区中同名相对路径的评论 key 如何包含根标识，以及重命名 / 移动文件的评论迁移规则，应在技术设计中定义并覆盖测试。
